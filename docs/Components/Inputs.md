# Input Components

> "Every question is the beginning of discovery."

---

# Purpose

Input components allow users to provide information, search, configure preferences and interact with astronomical experiences.

Inputs are the connection between user curiosity and AstroAlert knowledge.

They should make interaction feel:

- Natural.
- Clear.
- Comfortable.
- Intelligent.

Inputs should never create unnecessary friction.

---

# Content

# Input Philosophy

AstroAlert inputs follow the Cosmic Glass principle:

The interface should invite exploration, not request information.

Inputs should feel like scientific instruments:

- Precise.
- Simple.
- Elegant.
- Reliable.

They should not feel like traditional forms.

---

# Input Types

AstroAlert uses a limited set of input patterns.

Consistency is more important than creating many variations.

---

# Search Input

## Purpose

Help users discover astronomical information.

Examples:

- Planets.
- Stars.
- Missions.
- Events.
- Concepts.

## Behavior

Search should provide:

- Suggestions.
- Context.
- Related discoveries.

Example:

User types:

```
Mars
```

The system may suggest:

```
Mars
Mars Missions
Mars Atmosphere
Mars Observation
```

Search should become a discovery tool.

---

# Text Input

## Purpose

Collect short information.

Examples:

- User preferences.
- Profile information.
- Custom names.

## Characteristics

Should be:

- Clear.
- Spacious.
- Easy to read.

---

# Location Input

## Purpose

Enable astronomy experiences based on user position.

Examples:

- Visible planets.
- Eclipse visibility.
- Telescope recommendations.

## Principles

Location should be explained.

The user should understand why it is requested.

---

# Select Input

## Purpose

Choose from predefined options.

Examples:

- Telescope type.
- Observation conditions.
- Filters.

## Behavior

Options should be easy to understand.

Avoid technical complexity unless necessary.

---

# Range Input

## Purpose

Adjust values.

Examples:

- Telescope magnification.
- Distance filters.
- Time ranges.

## Principles

The current value should always be visible.

---

# Toggle Input

## Purpose

Enable or disable features.

Examples:

- Notifications.
- Astronomy alerts.
- Preferences.

## Behavior

The state must always be obvious.

---

# Input Anatomy

Every input contains:

---

# Label

Purpose:

Explain what information is needed.

Labels should always exist.

Do not rely only on placeholders.

---

# Field Area

The interactive space.

Should communicate:

- Availability.
- Focus.
- Current value.

---

# Helper Text

Purpose:

Provide additional guidance.

Examples:

"Used to calculate visible objects in your area."

---

# Error Message

Purpose:

Explain problems clearly.

Errors should help users recover.

Avoid technical messages.

---

# Input States

## Default

The input is ready.

---

## Focus

The user is interacting.

The interface should clearly communicate attention.

---

## Filled

The user has provided information.

The value should remain readable.

---

## Error

A problem exists.

The message should explain how to fix it.

---

## Disabled

The input is temporarily unavailable.

The reason should be understandable.

---

# Interaction Rules

## Rule 1

Every input must explain its purpose.

---

## Rule 2

Avoid asking for unnecessary information.

---

## Rule 3

The user should always understand the current state.

---

## Rule 4

Errors should guide, not punish.

---

# Visual Style

Inputs follow Cosmic Glass.

Characteristics:

- Soft surfaces.
- Clear borders.
- Subtle transparency.
- Strong readability.

Inputs should integrate with the environment.

They should feel like part of the spacecraft interface.

# Accessibility

Inputs must support:

- Keyboard navigation.
- Clear labels.
- Screen readers.
- Visible focus states.
- Understandable errors.

Information must never depend only on visual styling.

---

# Responsive Behavior

Desktop:

Inputs can provide more contextual information.

Mobile:

Inputs should prioritize:

- Clarity.
- Touch interaction.
- Simple completion.

---

# Design Implications

Input components affect:

- Search.
- Settings.
- Telescope tools.
- Filters.
- User preferences.
- Observation experiences.

New input patterns should only be created when a new interaction purpose exists.

---

# Final Statement

Inputs are not requests for data.

They are invitations for users to participate in exploration.

Every question entered into AstroAlert should open the possibility of discovering something new.
